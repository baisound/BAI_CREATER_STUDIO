# 口形下書きの区間編集（2026-11-19、#187）

順4、LIP-001/003。既存の発話別下書きは時刻・口形・強さを編集できるが、区間の数を変更できない。既存行の分割・削除と、画面内の区間編集の戻す/やり直すを追加する一単位とする。

上位3操作は区間を分ける、口形/強さ/境界を直す、下書きを保存して既存VMD出力へ進む。新しい画面や保存形式は作らない。ImpeccableのOperateとBAI UX Guardの基準で既存の編集行・固定操作を使う小規模拡張。全体再設計や音素解析エンジンは追加しない。

分割は整数フレームの中央を初期境界とし、元区間の開始・終了と口形/強さを保つ。1Fの区間と1000区間上限では分割不可。削除は少なくとも1区間を残す（発話全体の無音は既存の明示無音操作）。戻す/やり直すは同じ発話の画面内編集32操作まで。原SRT/読み/既存VMDと採用層を自動変更しない。再読込や発話切替では保存済み下書きから始める。

既存の共通APIと両MCPのlip_draft_saveへ同じsegmentsを保存する。未確定読み、元SRT/読み版/FPS/revision変更、範囲外/重複の拒否は維持する。保存処理中の編集を止め、未保存値を保存済みと誤認させない。

終了条件：分割/削除/入力の取消と再実行、境界/上限/最終行、保存再読込と発話切替、失敗/競合、既存VMDの実再読込とPMX反映の代表確認。手動/両MCP・OSの範囲を分け、原本保持、PR/main/8765同期まで。実歌詞54発話の読み確定や自然さの採用は行わず、LIP全体完成にも広げない。

モデル区分：高性能（既存仕様照合・実装・検証）。サブエージェントなし。

## 実装と代表検証

制作→タイムラインのSRT/読み欄で発話を選び、候補を計算した後、口形下書きの各行から「分割」「削除」を使う。中央分割後の開始/終了・形・強さは同じ欄で直す。「区間編集を戻す」「やり直す」はこの発話の32操作まで。「下書きを保存」の後は既存のVMD候補出力・確認・明示採用へ進む。画面内の履歴は再読込/発話切替でリセットし、保存済み下書きは残る。採用済み口形を編集で自動更新しない。

サイドバーで4列が見切れる問題を2列に修正。1440/1024の実画面を確認した。[1440px](../../studio/v05/reviews/lip-segment-editor-20261119/segments-1440.png)、[1024px](../../studio/v05/reviews/lip-segment-editor-20261119/segments-1024.png)。分割/削除と取消は実装済み。機械用の指摘LSE-01〜03・結果は同名STATUS JSON。

実PMX確認で、FPSを保存していない作品が口形30fps/映像60fpsになる既存不具合を発見した。今回の同時刻反映に不可欠な依存修正として口形候補/下書きを映像側の60fps既定へ揃えた。明示24/29.97/30/60fpsは維持。旧30fps下書きは値とファイルを変えず、従来のfps_changed表示で保護する。該当する下書きは正しい作品FPSを決めてから候補を再確認する必要がある。自動リタイムはしない。

最終：Windows/UbuntuのPython各34成功1skip（実歌声VMDの環境変数未指定試験）。ローカル編集3成功、Win既存SRT/合成VMD・MP4回帰2成功。両OSの実Chromeで分割/削除/取消、保存ロック、保存競合時のローカル保持、発話切替/再読込を各1件成功。Windowsは公式SDK/ネイティブWebMCP、UbuntuはSDKを通した同じ下書き保存APIを確認。型検査とUI検出器も成功。
