# G3-A2：入力振幅とAAC境界差の分離（2026-11-09）

順3、#81/#39/#63、AUDIO-001・RENDER-006。[G3-A1](AAC_BOUNDARY_DIAGNOSTIC_20261108_JA.md)の次工程。参照加算に最大1.282292/範囲超過48チャンネルサンプルがあったため、その寄与を直接AACの対照で調べる。

## 試験契約

- 同一の原WAV/MP3・配置/元位置/尺から、A1と同じ48kHzステレオPCMを再構成し、参照PCM hashが一致すること。
- AAC192kb/s・同じエンコーダーで振幅1/0.75/0.5を比較。解析時に倍率を戻し、元参照に対する音量比/相関/誤差を測る。倍率0.75/0.5では入力の絶対値1超過が0になることを検査する。
- 絶対値1でクリップした独立対照を追加し、クリップによる入力変更とAAC圧縮後の差を分ける。この処理は診断用ファイルのみ。
- 6境界×9位置×20/50/200msの162窓、±4sampleの相関探索をA1と同じ条件で測る。倍率1は同じOSのA1対照と162窓の波形hash一致を確認する。
- 原本・索引・既存完成MP4は前後hash不変。新しい確認フォルダーを排他的に作成し、旧出力を上書きしない。Windows/Ubuntuを区別する。
- 合格は入力条件の分離・再現・保全の検証に限定。3%未達、G3-A/順3全体の完成度、主観聴感は変更しない。製品の時計・音量・自動減衰・フェード・ミキサー・codec設定を変えない。

モデル区分：高性能（因果の切り分け・実装・実測判断）。

## 入力倍率比較後の追加診断

0.75/0.5倍では210秒窓が改善し、絶対値1でのクリップだけではUbuntu側が3%以内にならなかった。音量を保つ既存要件に照らし、次の必要診断として振幅1のままAAC192/256/320/384kb/sを比較する。比較条件を増やした理由は、入力を自動減衰する修正を採らずに圧縮設定の寄与を分離するため。これも新規の診断対照だけであり、製品の設定・出力上限・受入れ基準を変更しない。


## 結果と判断

両OSの参照PCM hashはA1と一致。倍率1の192kb/s対照は各OSのA1対照と162/162窓のPCM一致。倍率0.75/0.5とクリップ対照は全て範囲超過0、クリップで変更した値は48チャンネルサンプルだけだった。原本/索引/旧MP4は前後不変。

|---|---:|---:|
| 振幅1・192kb/s | 0.970141 | 0.959620 |
| 振幅0.75・192kb/s | 0.995587 | 0.978903 |

倍率を下げると改善し、48値のクリップだけではUbuntuの既知窓が3%以内にならない。過大入力/レベル依存の寄与はあるが、単純な48値のハードクリップだけを原因として説明できない。AAC圧縮の設定にも依存する。これをAAC内部アルゴリズム全体の証明とはしない。

振幅1・320kb/sは、各OSの200ms/54窓すべてで差3%以内（最小比Windows0.974190/Ubuntu0.971968）、既知210秒窓lag0。256kb/sではWindows1窓/Ubuntu6窓が3%超、192kb/sでは4窓/6窓。320kb/sでも20/50msを含む全162窓の無劣化は保証せず、短窓の未達は残る。音声だけの対照容量は192→320でWindows5,529,434→9,182,911bytes、Ubuntu5,626,375→9,339,192bytes。完成MP4全体の増加率は映像に依存する。

G3-A2の分離診断を確認済みとする。入力音量を勝手に下げる修正を採らず、次の必要修正G3-A3として新規MP4のAAC320kb/sを実際の製品経路で検証する。既知の製品192kb/s出力の3%未達とG3-A/順3全体は、この対照結果だけで閉じない。

## 途中失敗・再実行

Windows384kb/sの対照が高CPUのまま長時間進まなかった。出力先/コマンドで所有FFmpeg PID48336を確認して停止し、未完走として保持。診断FFmpegへ120秒上限と各対照の途中記録を追加し、Windowsは192/256/320だけのbitrate-320モードで完走した。384の成功へ数えない。Ubuntuは4条件完走済み。最終の終了記録追加は数値処理へ作用せず、Windows倍率4条件で確認した。
