# MOTION-010 元VMD曲線と物理フラグ領域の調査

2026-10-24。Issue #106。密な元VMD曲線を含む候補を安全に作れるか調べた。今回の入力は候補生成を拒否し続ける。曲線分割の新しいwriterは採用していない。

## 観測

登録済み`神っぽいな.vmd`の`頭`骨では、VMD F209→221の原キー間に補正のVMD F210キーが挿入される。作品F169付近で元の回転曲線が切れて局所角度差が`0.26384221°`に達し、現在の上限`0.01°`で候補生成が拒否された。`頭`骨の元キーは1087件で、F180〜250には196、206、209、221、227、231、239、246のキーがある。

原VMDのF221キーで64バイト補間の先頭4バイトは`[20,20,0,0]`、シフト複製部分の対応バイトは`[20,20,20,20]`。短尺の別VMDも同様の差を持つ。Three.js r160の`MMDLoader`は先頭16バイトから補間制御点を読み、現在のPython局所ゲートも同じ解釈である。一方、[VMD補間のリバースエンジニアリング資料](https://github.com/skyflash521/mmd-toolbox/blob/main/docs/specs/vmd/VMD_file_format.md)は、先頭16バイトとシフト複製が異なる場合に物理フラグ領域との重なりがあり得ると記す。公式仕様ではないため、この差だけでフラグ値の意味を確定しない。

単純なBezier分割で元キーの補間64バイトを書き直すと、別プレイヤーの物理状態を変える可能性がある。候補の検査はThree.jsの物理OFFで実行されるため、画面の合格表示にも「物理OFF」を追加した。元の64バイト、物理フラグ、補間を保ちながら分割できる条件と、対象プレイヤーでの実再生を確認するまで、この密な入力は拒否を維持する。

`npm run typecheck` と隔離Chrome/SwiftShaderの `node tests/run-guarded.cjs tests/studio-v05-vmd-fps-fade-real.test.cjs` は成功。画面の「物理OFF」表示、実PMXの作品240F＋VMD300F×201骨の一致、`data/`7ファイル・`exports/`0ファイルの前後ハッシュ一致を確認した。
