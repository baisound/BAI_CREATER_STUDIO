# MOTION-010 動くVMD曲線を密キー化するときの境界検査

2026-10-24、Issue #106。全フレーム候補で動く元VMDを実PMXに戻すと角度0.0369°の差が出た原因を、Three.js r160のVMD補間と実データで切り分けた。元VMDは保持し、全フレーム候補で再現できない入力を候補ファイル作成前に拒否する。

## 原因と対応

`MMDLoader.js`の`CubicBezierInterpolation`は、隣接キーの間隔が1/30秒付近なら補間重みを0にする。その後の15回二分探索は、重み0でも厳密な0を返さない。今回の実VMDにある制御点では`_calculate(..., 0)`が約0.00092877になる。元の疎なキーでは次キーまでの角度差にこの値が掛かるが、全フレームキーを挿入すると次キーが1フレーム先になり、元キー時刻の表示姿勢も変わる。実VMDのF120では元曲線と密キーで頭の角度が約0.0369°異なり、仕様上限0.01°を超えた。元キーのbyte保持と毎フレームのキー化を同時に守る範囲では、この入力を忠実に書き出せない。

全フレーム候補の局所検査に、Three.jsの境界補間を再現した全VMDフレーム比較を加えた。元曲線と候補の最大誤差・該当フレームを計算し、閾値を超えたら候補作成APIを422にして日本語の理由と数値を返す。既存の実PMX全骨・全フレーム検査は別ゲートとして残す。旧方式の疎な候補は明示選択できる。

## 検証

- 実データ不要の合成VMDで、F30の境界角度差を再現して拒否する単体試験を追加した。実VMDでもF120・角度約0.036913°を候補作成前に検出し、元ファイルのSHA-256不変を確認。
- `python -m pytest -q tests/test_studio_v05_vmd_full.py tests/test_studio_v05_vmd_adoption.py tests/test_studio_v05_vmd_partial.py tests/test_studio_v05_vmd_temporal.py`: 実素材指定で23件成功。
- `npm run typecheck`成功。
- `node tests/run-guarded.cjs tests/studio-v05-vmd-full-real.test.cjs`: 隔離Chrome/SwiftShaderで2件成功。静止頭骨の全フレーム候補は246骨PMX、作品150F＋VMD301Fで合格し採用・復元した。動く元VMDは候補作成APIで422となり、元クリップの登録素材IDと実素材7ファイルの前後ハッシュを維持した。

全フレーム方式が扱える入力を明確にする改善であり、動く元曲線の万能な密キー変換ではない。異なるFPSや補間の全組み合わせ、物理ON、実GPU、Linux、標準MCP、Owner採用とMOTION-010全ACは未確認。MOTION-010は「要検証」。画像・動画の納品成果物は制作しておらずEagle登録対象なし。モデル区分: 原因調査・実装・試験・文書化に標準モデル区分を使用。
