# MOTION-010 動く元VMDの密キー区間が失う姿勢

2026-10-24、Issue #106。90秒付近の区間候補が拒否された理由を、登録済み `神っぽいな.vmd` の頭骨曲線と現行MMD評価器で分けて調べた。元VMDは読取のみ。

- Three.jsのMMDLoaderは、次のVMD骨キーが1/30秒以内の隣接フレームにあると、その間の姿勢を前キーの値に保持する（`node_modules/three/examples/jsm/loaders/MMDLoader.js` の `weight1` 条件）。サーバー側の候補検査も `studio_v05_vmd_temporal.py` の `_pose` で同じ条件を使う。
- 元VMDの頭骨キーは90秒付近でVMD F2707からF2713へ動く。区間候補が間へF2708等の密なキーを加えると、作品60fpsのF5415（VMD F2707.5）では候補がF2707の姿勢を保持し、元の動く曲線との差が生じる。
- 補正量を完全に0にした対照実験でも、元キー境界 `[2669,2732)` へ密キーを加えるだけで最大角度差 `4.909817°`（作品F5415）、区間外を含む差 `0.031324°`。前後のなじませを2、4、8、16、32、48作品フレームへ変えてもこの角度差は残った。実際の頭骨Y12°・X位置0.15の補正では、なじませ2Fの最大位置差 `0.074998`、最大角度差 `6.073634°`。なじませ48Fでも位置差 `0.003125`、角度差 `4.909818°` で受け入れ上限を超える。
- `tests/test_studio_v05_vmd_partial.py` に実VMD・補正量0の回帰を追加。なじませ2F/48Fとも拒否とF5415の角度差を確認。`python -m pytest -q tests/test_studio_v05_vmd_partial.py` は9件通過。最初の実行はWindows隔離環境の既定TEMPで権限エラーとなり、作業用一時領域を指定して再実行した。入力VMDの前後バイトは一致。

この観測から、**現行評価器で隣接30fpsキーを密に並べるだけでは、動く元曲線の60fps中間姿勢を表現できない**と判断する。単純に密キー数を増やす修正は採用しない。元の疎な曲線を保持できる一定補正の範囲と、時間限定補正を安全に表現できる範囲を別ゲートで検査し、誤差超過は拒否する。任意の時間変化を持つ全入力の別名VMD完成は未達。
