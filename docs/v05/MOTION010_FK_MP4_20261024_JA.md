# MOTION-010 FK補正入り完成MP4の画素と姿勢の照合

2026-10-24、Issue #106。[レイヤー・タイムライン接続](MOTION010_FK_LAYER_TIMELINE_20261024_JA.md)後の書き出し検証。作品に登録した実PMXと実VMDを、元MP4、同条件の元MP4再出力、頭骨FK補正入りMP4、補正レイヤー重み0のMP4として**別ジョブ**で出力した。3F限定のゲートであり、MOTION-010全体や別名VMDの完了ではない。

## 変更した点

- 重み0の保存レイヤーはPMXの補正評価器を起動しない。元VMDだけの既存評価経路で描く。重み0でも骨の補正ループ自体は何もしないという従来の状態より、元経路との一致を明確にした。
- 各完成MP4ジョブの`scene_capture.motion_edits_revision`に、キャプチャ開始・終了で一致を確認した作品別FK補正revisionを記録する。既存のmanifest検査と同じ原本から取り、欠けた/不正なrevisionならジョブを失敗にする。

## 実データ確認

試験は`tests/studio-v05-pmx-fk-mp4.test.cjs`。隔離した作品へ実PMXと10秒VMDを登録し、F240〜F242を720p H.264 MP4へ4回書き出した。3D画面が決めたカメラを作品へ保存し、4回とも同じシーン・モーション・カメラ・範囲を使用。保存補正はF240の頭骨へY軸45度のローカル四元数差分。ジョブの補正revisionは順に0/0/1/2で、頭骨差分は0.390085、無関係のセンター骨差分0、重み0の頭骨差分0だった。

完成MP4を復号して同じF240の1280×720 RGB画素を比較。最終の連続回帰で、1色成分でも差が5を超える画素は、元MP4をそのまま再出力した比較で754、FK補正入りとの比較で8,786、重み0との比較で868だった。別の単独実行では順に2,256/9,868/1,688で、再出力自体に小さな画素揺れがある。完全byte一致ではなく、FK補正差が同条件再出力差の2倍を超え、重み0差が再出力の揺れと分離できる範囲に収まることを判定する。元MP4は後続ジョブ後も同じSHA-256で読めた。

`BAI_REAL_MMD_DATA=<既存data>`、`CHROMIUM_PATH=<Chrome>`、`BAI_TEST_CONCURRENCY=1`で`node tests/run-guarded.cjs tests/studio-v05-pmx-pose-evaluator.test.cjs tests/studio-v05-pmx-fk-edit-real.test.cjs tests/studio-v05-pmx-fk-mp4.test.cjs`を実行し3/3成功。`npm run typecheck`、Python/JS構文、`git diff --check`も成功。初回比較は重み0でも補正評価器を有効化する状態と自動カメラ構図の差が混ざり、試験ゲートを通らなかった。重み0の経路修正と保存カメラ固定、元MP4の再出力を追加して再測定した。

レンダラーはNVIDIA GeForce RTX 4070 SUPER / Direct3D11を報告した。元PMX SHA-256 `542a4daa561f0b0da578fc303af9b8c6dc4acdd8d380771a170e96e95a205488`、元VMD SHA-256 `3ae724f9d1d36a7e74a911d6b1bbfad7d2459e5e256fcac43521ebebd0a3d234` は前後一致。`run-guarded`が利用者`data/`7ファイルと`exports/`の前後ハッシュ一致も確認した。試験のMP4は隔離一時領域の検証出力で、作品成果物として納品していない。

## 限界

このゲートは実PMX/実VMD1組、3F、頭骨回転1キー、保存カメラ1視点を対象とする。長尺90秒、手足IK、複数レイヤー、表情との同時補正、Linux、別名VMD書き戻し、WebMCP/標準MCP実呼出し、Owner採用は未確認。補正なしの元MP4同士にも画素差があるため、画素の完全一致や全フレームの品質を主張しない。MOTION-010全体は「要検証」のまま。
