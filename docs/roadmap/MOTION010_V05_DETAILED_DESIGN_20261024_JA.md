# v0.5 任意フレームの骨補正 — MOTION-010 詳細設計

2026-10-24。対象は Issue #106、[Ownerの実施順](V05_MINIMUM_WORKFLOW_20261023_JA.md)の順5と[承認済み要求](RIG_EDITING_SPEC_20261020_JA.md) §2。ここではPMX＋VMDを先行する。設計の最終判定は末尾に記録する。この文書だけで実装・動作品質・Owner採用を完了扱いにしない。

## 1. 利用者に見せる結果と実装の区切り

同じv0.5作品の3D編集画面で、対象PMXインスタンス、結び付いたVMDクリップ、作品フレーム、骨を明示してポーズ補正する。原VMDとPMXは読み取り専用。補正はその作品の別データに保存し、元動作との重ね合わせを再生・書き出しに使う。別名VMDは実再生と往復誤差を確認してから利用可能と表示する。

| 区切り | 追加する操作 | 合格を主張できる範囲 |
|---|---|---|
| A | PMXのFK回転1骨を数値でプレビュー→確定、作品別のキーとレイヤー、Undo/Redo、同時刻の3D再生と保存再読込 | 限定した骨・実PMX/実VMDの画面内補正。VMD書き出しはまだ無効 |
| B | 3D回転ギズモ、腰/胸/頭と任意FK骨、位置チャネル、部位別FK/IK切替・手足ハンドル、3D IKの到達/制限表示 | 対応ハンドルと部位だけ。未対応ボーンは理由付きで操作不可 |
| C | VMD全フレーム/修正区間だけの別名書き出し、元VMDの非骨区画保持、読み戻しと実PMX再生比較 | 許容誤差内の対象入力だけ「書き出し確認済み」。失敗時は出力を採用しない |
| D | VRM、MOTION-011自動接地、MOTION-014ゴースト/軌跡、全入口・OSでの照合 | 各要件IDの別ゲート。A〜Cの成功から推定しない |

区切りAでも利用者が3D上の骨を選べるアウトラインと数値編集を用意する。3Dギズモ、IK、VMD書き出しの操作部を見本だけで有効にしない。後続の追加は同じ作品ID・クリップID・シーンインスタンスID・時刻・API・保存形式を拡張する。

## 2. 確認した既存実装と再利用境界

- `studio/v05/js/multi-model-ui-v58.js`と`multi-model-motion-v59.js`は作品の複数インスタンスを一つの描画器で持ち、対象ごとにモーションを評価する。`sceneSnapshot`にはrevision、ロック、PMX表情キーがある。v0.5の同じ3D表示を編集ビューに用い、新しいWebGL描画器を重ねない。
- `studio/js/motion/player.js`のPMX VMDはThree.jsの`MMDAnimationHelper`で素のVMD姿勢、IK、grantを順に評価し、物理はOFF。現行の`seek`は補正を挿入する公開フックを持たない。Three.js側の`_animateMesh`は`_restoreBones`→mixer→`_saveBones`→IK/grantの順である。IK後に補正するだけでは、足や付与骨の書き出し結果と一致しない。
- 旧`motion_layers.js`/`studio/js/motion/layers.fork.js`はグローバルな`data/motion_layers.json`（schema 1、revisionなし、1骨Euler XYZ加算、線形補間）を使う。これはv0.5の作品・クリップを区別できず、MMDのIK/grant前補正や重み・区間を表せない。旧ファイルを移動・初期化・上書きせず、読み取り専用の明示インポート候補として扱う。
- `pose_ik.py`はXY平面の2関節解であり、3Dハンドルの実装ではない。`motion_vmd_bridge.py`は明示対応の生チャネル変換で、元VMDのモーフ等を保持する編集用writerではない。`vmd_readback.py`は骨区画の構造読取だけ。どれも完成済みの骨編集や安全な書き出しとして呼ばない。
- `studio_v05_scene_instances.py`と`studio_v05_multi_motion.py`が作品、実在インスタンス、ロック、モーションクリップの検証に使える。登録素材のパス解決・SHA-256は既存の別名VMD経路の安全境界を踏襲する。

## 3. 操作と画面

1. 編集画面の既存3Dプレビューを「姿勢修正」モードへ切り替える。プレビュー再生を停止し、作品フレームと作品FPS、対象PMX、結び付いたVMD、補正対象の骨とレイヤーを固定表示する。別作品や別インスタンスへ移る際は未確定プレビューを破棄する。
2. 右側の「リグ」区画はアウトラインと対応状態、選択骨のFK回転/位置、部位のFK/IK、オートキーを持つ。「補正レイヤー」区画は名前、順、0〜100%重み、有効区間、前後なじませ、ミュート/ソロを持つ。既存の表情/口、足診断、カメラは別区画に保つ。狭い画面では区画内だけをスクロールする。
3. 数値やギズモの操作中はメモリ内プレビューだけを変える。`Esc`で操作前の姿勢へ戻す。オートキーONなら離す/Enterで変更したチャネルだけを1回保存して1 Undo、OFFなら「未確定」と［キー化］を示す。初期値は誤保存を防ぐためOFF。FK/IKの切替自体はキーとUndoを増やさず、見た目の姿勢をスナップして保つ。
4. 未対応骨・VMD名の15 Shift_JISバイト超・ロック済みインスタンス・有効なVMDのない時刻・重複モーションクリップは操作ボタンを無効にし、理由を出す。グレーのハンドルは選択できるが確定できない。
5. 作品タイムラインの同じフレームに補正キーを表示し、元クリップ、PMX表情キー、補正キーを区別する。補正キーの移動・削除はそのクリップとボーンだけを変更する。撮影ビューとMP4にはハンドルやギズモを写さない。

## 4. 保存、競合、旧データ

正本は`data/studio_v05_motion_edits/<project-id>.json`の作品別ファイル。`project_id`は作品カタログで検証し、パスへ外部文字列を直接連結しない。schema 1、revision、`layers`、`fk_ik_modes`、`history`を持つ。各レイヤーには固定ID、対象`instance_id`と`clip_id`、原PMX/VMDの素材ID・SHA-256、作成時の作品FPSとclip開始/長さ、名前、順、重み、区間 `[start_frame,end_frame)`、なじませ、ミュート/ソロ、チャネル/キーを持つ。キーは作品フレーム整数、PMX骨名、位置差分または正規化したローカル四元数差分、補間4チャネルの制御点を持つ。補間の既定は線形で、後で`DATA-003`の曲線部品から編集する。

オートキーON/OFF、選択ハンドル、座標軸、ゴースト等の表示設定は編集用workspaceとして作品別に保存し、作品の書き出しデータに混ぜない。段階AではオートキーOFFを既定とし、未確定プレビューは保存しない。UIの状態保存に失敗しても元VMDや補正キーの正本は変更しない。

保存時に作品・クリップ・インスタンス・素材の実在、PMX/VMD形式、ロック、SHA-256、フレーム境界、有限数、四元数ノルム、重複キー、制御点範囲、レイヤー/キー件数をサーバーで検証する。別の作品や変更された元素材へ自動で適用しない。作品FPS/クリップ位置/尺が変わった場合は旧フレームを無断でずらさず、補正を停止して利用者に再配置を示す。保存済みファイルの破損は空データへ黙って置き換えない。

`GET /api/studio/v05/motion-edits?id=...`は現在のrevisionと保存内容、元素材・配置の一致状態を返す。`POST`は`project_id`、`revision`、対象ID、`action`、変更値を受け、既存のrevision付き保存方式と同じロック・atomic replaceを使う。競合はHTTP 409で上書きしない。1確定=1履歴、上限80。Undo/Redoもrevision付きの同じAPIへ送る。ブラウザの手動UIとWebMCP、標準MCPはこの共通APIを呼び、ブラウザ内のドラッグプレビューだけは標準MCPから不可と明記する。

旧`motion_layers.json`はそのまま旧UIで読める。v0.5では読み取り専用で一覧・ハッシュを表示し、対象作品/PMX/クリップと骨名を人が選んだ場合だけ別名のインポート候補を作る。旧Euler角の足し算を四元数差分と同一視しない。元の旧画面との同フレーム視覚照合ができない候補は保存を拒否する。旧グローバルファイルへv0.5から書き戻さない。

## 5. 評価計算と骨操作

プレビュー・固定フレームMP4・書き出し検査は同じフレーム番号と補正データrevisionを指定する。PMX VMDの各フレームで、素のVMDキーを評価し、`MOTION-011`自動接地（実装時のみ）を反映し、レイヤーを下から順に加算してからIK/grantを一度解く。回転は`q_base × slerp(identity,q_delta,w)`、位置は`p_base + w × delta`。重み`w`はレイヤー重み、区間、なじませ、ミュート/ソロの積。0%は元姿勢と一致させる。選んでいない部位に補正キーを作らない。

`MMDAnimationHelper`の非公開内部へ無条件に割り込まない。限定したThree.js版で、既存の`seek`と同じ順番の評価器を明示的に作り、mixer後・IK/grant前に補正を挿入する。補正なしの新評価器が0/4/90秒、往復シーク、表情で現行描画と一致しなければ切り替えない。IK/grantの二重適用や前フレームからの補正累積を許さない。Three.js内部契約が変わればエラーで補正機能を停止し、元の再生を保つ。物理は既存のOFF条件を維持し、物理品質を主張しない。

IKはPMX足IKのターゲット骨を優先し、腕とVRMでは別の3D二関節解を作る。ワールド座標の目標をモデルの親空間へ変換し、関節長・ポール・角度制限から解く。届かない目標は距離と到達点を報告する。FK/IK切替の前後で全骨の世界座標を比較し、規定の誤差を超える場合は切替を中止する。`pose_ik.py`のXY解はこの3D解の代用品にしない。

## 6. 別名VMDと往復検査

出力は原VMDを読み取り、新しい名前だけに書く。ヘッダーと骨区画を厳密に検証し、骨区画の後ろ（モーフ、カメラ、照明、影、IK切替等を含む）を不透明なbyte列として**そのまま複写**する。補正しない元の骨レコードもbyte列を保持する。対象の骨・VMDフレームだけ、新しい位置/四元数と補間を記録する。重複骨フレーム、不正長、不正CP932名、非有限値、過大件数は拒否する。出力ファイルの登録と作品への配置は生成検査後に行い、失敗時に原本・既存VMDを保持する。

全フレーム出力を既定にし、修正区間だけの出力も提供する。元VMDは30fps、作品FPSは別なので、作品フレームの補正をVMD各フレームの時刻へ評価して焼く。作品の細かなキーが30fpsで再現できない場合、フレーム丸めで黙って落とさず、最大位置・角度誤差と該当フレームを出して合格を拒否する。VMD書き戻し後に`vmd_readback.py`の骨検査、元VMD非骨区画のbyte一致、実PMXを同時刻に再読込した姿勢差を全出力フレームで検査する。閾値は要求の位置1e-3 MMD単位・回転0.01°。長尺は有界ジョブとして進捗と失敗理由を出す。足は元VMDのIK使用状態に従い、別方式へ勝手に切り替えない。ライセンス判定はせず、原VMDの配布規約に従う注意を出す。

## 7. 試験契約と記録

- 単体: 四元数合成、重み0/50/100%、区間外/なじませ、ベジェ/保持/線形、オートキーON/OFFと既存キーの組合せ、Undo/Redo 80件、競合、ロック、元素材変更、骨名/フレーム/有限数の拒否。
- 計算照合: JSのプレビュー計算とPythonの焼き込み計算を共通fixtureで比較する。PMX IKの解はThree.js画面の実骨ワールド座標で測る。FK/IK切替の1e-4、手先到達の1e-3を確認する。
- 画面: 実PMX＋実VMDで1骨を動かし、元/補正姿勢、別骨不変、Esc、1操作1キー1 Undo、保存再読込、0/4/90秒、限定MP4の画素と姿勢を確認する。SwiftShaderと実GPUを区別する。
- VMD: 全フレーム/修正区間だけの別名出力、原本SHA-256不変、非骨区画byte一致、区間外骨レコードbyte一致、実PMX再生の最大誤差・位置を記録する。出力不合格は採用候補へ昇格させない。
- 入口: 手動UI、共通API、WebMCP、標準MCPが同じ保存結果を作ることを照合し、ドラッグのライブプレビュー等の制限を列記する。WindowsとLinuxを別に記録する。

## 8. 未決事項の扱い

最新ロードマップ順5がO-01の実施時期を定める。VRM/VMD経路(O-02)と制限(O-12)、ゴースト(O-09)、コピー/貼り付け(O-10)は依存設計へ保留する。重みキー、上書きレイヤー、スタック順変更、look-at、連続記録は作らない(O-03/04/05/08/13)。間引きは作らず全フレーム出力を既定にする(O-06)。足の出力方式は元VMDに従う(O-07)。オートキー既定OFF、時間区間のIK/FK混合なし(O-11)。IK計算の正本はサーバーとJSで共通fixtureを通す(O-15)。Undo上限80(O-16)。区画は「リグ」「補正レイヤー」を既存プレビュー内の切替区画にし、表情・足診断と同時に全面表示しない(O-17)。

## 9. 設計批評3回と最終判定

### 第1回 — 保存と既存データ

指摘: 旧`motion_layers.json`を直接使う案では、作品やクリップを切り替えても同じ補正が当たり、revisionなしの上書きで旧UIの編集も失われる。修正: 作品別の新正本へ`instance_id`/`clip_id`/素材ハッシュ/配置を固定し、旧データは読み取り・明示インポート候補に限定。HTTP 409と80件履歴を設計に追加。判定: 作品間の誤適用経路を閉じた。

### 第2回 — 3D姿勢と書き出しの一致

指摘: 旧Euler加算やIK後の単純な四元数加算はPMXのIK/grantを二重にしたり、画面とVMDで別の姿勢を作る。修正: mixer後・IK/grant前の単一評価順を要求し、補正なしの既存結果とのA/B比較、往復シークでの累積検査、JS/Python fixture、VMD再読込の実骨誤差をゲートに追加。非公開Three.js内部が変わる環境ではfail closed。判定: 見た目をAPI成功だけで認定しない。

### 第3回 — 時間・部分出力・画面

指摘: 作品FPSとVMD30fpsを同一視すると任意フレームの補正が消える。骨区画だけを書き直す際にモーフやIK切替まで落とす危険がある。旧モーダルに操作を増やすだけでは使いにくい。修正: 出力をVMD30fpsへ標本化し誤差超過を拒否、非骨suffixと区間外骨レコードのbyte一致、区画切替と機能未実装の明示を追加。判定: 出力とUIの境界は検証可能。

### 最終判定

上の修正を反映した詳細設計を**段階Aの実装入口として採用**する。段階Aの受け入れは作品別保存・revision/Undo・同じPMXの実プレビュー・保存再読込・原本ハッシュ不変・既存描画との補正ゼロ一致まで。段階B〜D、別名VMDの品質、全AC、Owner採用はこの判定に含めない。段階Aの前にThree.js評価順の無補正A/B試験を作り、結果が異なれば補正機能の公開を止めて原因を直す。三回の批評はこの文書の別視点レビューとして記録し、独立した第三者レビュー済みとは称しない。
