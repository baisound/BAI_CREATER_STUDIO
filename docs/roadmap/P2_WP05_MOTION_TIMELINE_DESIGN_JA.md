## 2. データ境界と保存

| 正本 | 既存形式 | WP-05の扱い |
|---|---|---|
| `project_state.json` | `schema:1`、`timeline:[{name}]`、`history`、`cursor`、`selected`、`playbackSpeed` | 連結順の正本。P2-WP-01の `project` ストアを通じて変更し、450ms自動保存・If-Match・外部変更検出を再利用。`history` は旧画面と同じ最大100件。詳細クリップはここへ混ぜない |
| `timeline_editor.json` | `schema:1`、`clips:[{name,start,duration,speed,blend}]`、`updatedAt` | 詳細編集の正本。最大200件・256KiB・範囲制限は現行APIと同じ。550ms自動保存。連結順からの取り込みはコピーであり、既存の詳細編集を置換する場合は件数を示して確認 |
| `favorites.json` | `[{id,name,tags,steps:[{name}]}]` | お気に入りの正本。現在の連結順から別名保存／既存IDの上書きを明示。お気に入り削除は原本FBXや編集中の連結順を消さない |
| `workspace`（統合バンドルschema1） | `asset`、`clip`、`frame`、`stage` | `frame` は停止・明示シーク時だけ、0以上かつカメラduration以下に丸める。`clip` は `asset` がGLB/VRMの場合の0始まり番号だけ。PMX＋VMDとFBXは `clip` に書かない |

`combination.timeline` と `timeline_editor.json` は別データであることをUIに「連結順」「詳細タイムライン」と明記する。読み込みは常にコピーで、既存の詳細クリップがある場合は「現在の詳細クリップ N 件を置き換えます」と確認する。取り込む各ステップは旧UIと同じ初期値 `duration=90F, speed=1, blend=6F`、開始は前の終了Fとする。FBXの実長が90Fと異なる可能性を表示し、ユーザーが数値を調整できる。取り込みが途中で失敗したら既存の詳細クリップを維持する。

上部の保存表示は二つの状態を区別する。「連結順」はP2-WP-01の自動保存、「詳細タイムライン」は別APIの550ms自動保存である。片方の保存成功を「すべて保存済み」と表示しない。詳細保存の失敗・409・送信待ちがある間に画面を離れるときは未保存警告を出す。既存のプロジェクトUndo/Redoは連結順だけを戻す。詳細編集に全体Undoを追加することはWP-05の既存機能移植には含めず、［保存済みを再読込］は現在の詳細編集を破棄する確認付き操作とする。

新UIの連結操作は `project.js` に狭い `editCombination(change,label)` を設け、読み込めている `combination` をコピーし、入力と登録を検査してから1回でストアへ反映する。連結順は既存WebMCPと同じ最大100ステップとし、パターンの全ステップが入らない場合は1件も追加しない。履歴の分岐後を切り捨て、変更後のスナップショットを最大100件で記録し、既存 `scheduleAutosave()` を使う。検索・シーク・再生は履歴を積まない。Undo/RedoはP2-WP-01の履歴を使い、外部変更と409ではローカルの未保存編集を消さない。

### 2.1 同時編集の防止（O-⑤-4）

現行の「POST直前にGETして `updatedAt` 比較」だけでは、GETとPOSTの間の書き込みを検知できない。`/api/timeline-editor` のGETに現在のファイル内容から計算した `revision` を追加し、POSTは `EDITOR_LOCK` の中で `If-Match` と現行revisionを比較する。異なれば409で書き込まない。POST成功時にも新revisionを返す。保存ファイルの `schema:1` と既存フィールドは変えない。revision は `sha256(保存ファイルの生バイト列)` の16進小文字64字。ファイルがまだ無い場合だけ文字列 `missing` とし、0バイトや壊れたJSONは欠損とみなさず422で止める。既存の `editor_read()` の壊れたJSONを空タイムラインへ置き換える経路はこの時点で修正する。新UIと標準MCPの書き込みはrevisionを送る。**旧 `index.html` と旧 `webmcp.js` はR5に従い変更しない**ため、ヘッダーなしの互換経路は従来どおり受け、同時編集の保護対象外と診断ログに記録する。

`/api/favorites` の一覧更新も同じ方式でrevisionを返して比較する。旧形式の配列応答を使うクライアントがあるため、GETの既定の本文は配列のままにし、`?envelope=1` のときだけ `{favorites,revision}` を返す。POSTの `If-Match` は任意ヘッダーとして追加する。ファイル欠損と壊れたJSONの扱いは詳細タイムラインと同じ。409後はUIが自動上書きせず、再読込かキャンセルを選べる。両APIとも読み込み・比較・置換を同じロック内で行い、一時ファイルは `BAI_DATA_DIR` の対象ディレクトリに置く。元のJSONを失敗時に残す。お気に入りに今は未登録の名前がある場合、行を消さず「素材がありません」と表示し、再生だけ止める。

## 3. 再生とアセットの評価

1. **入力の解決**：82件の `rows` は旧 `index.html` の配列を `studio/js/motion/patterns.fork.js` へ値だけ写し、ID・名称・Mixamo名・`steps`・分類・元データを保つ。原本の配列と機械比較する。FBXステップ名はまず既存 `/api/manifest` の `mapping`（利用者が保存した対応）を使い、無ければ旧 `norm()` と同じ「小文字化・`.fbx` 除去・英数字以外除去」で登録済みモーション名と照合する。一致が0件または複数件、割当先のFBXにアニメーションが無い、読込に失敗した場合は、そのステップ名と理由を示して再生・追加を止める。名称の推測で別モーションを代用しない。対応表の編集は既存 `/api/mapping` を使用する。一覧の可否はメタデータで判定し、巨大なFBXを82件まとめて解析しない。プレビュー対象の実ファイルだけ読み、画面離脱・対象変更時には古い読込結果を採用せず破棄する。
2. **1つの評価器**：`studio/js/motion/transport.js` が `playSingle`、`playChain`、`playTimeline`、`seek`、`stop` を持ち、3モードが同じモデルと3Dホストの再生時計を使う。ブラウザーの時間差は最大80msに制限し、タブ復帰後の飛び越しを防ぐ。停止・画面離脱時にRAF、mixer action、イベント購読を解除する。
3. **連結再生**：旧 `chainFrame`・`clipOffset` を関数単位で `chain.fork.js` に写す。区間境界は実クリップの秒数から決め、`playbackSpeed` を全体に掛ける。前ステップまでの hips/root のX/Z差分を絶対値として毎フレーム再計算し、スクラブ・ループで累積ずれを出さない。Y変位、床接地、IK、物理は追加しない。元FBX・VMDは変更しない。
4. **詳細タイムライン**：開始F以上・終了F未満のクリップを候補にし、重なり時は旧 `timelineFrame` と同じく開始順で最後のクリップを選ぶ。ローカル秒は `(現在F−開始F)/30×速度`。クリップ切替時の `blend` は最大120Fの既存挙動に合わせ、実際の3D再生で変化を測る。空白区間はモデルを停止し、次のクリップまでワープさせない。速度・ブレンドが見た目に反映されないなら「実装済み」としない。
5. **形式別**：GLB内アニメーションの選択・シークは既存 `camera_3d.js` とWP-04のモデルローダーを利用する。PMX＋VMDは旧 `MMDLoader.loadAnimation` 経路を移し、VMDに含まれるボーンと既存モーフ（口・表情）のキーを再生する。実PMX/VMDでのモーフ検証ができなければ未検証と記録する。VRMへのVMD適用、複数人物の同期、MMD物理の追加は対象外。
6. **2D模式アニメーション**：旧画面の前・再生・次・速度・シークをSCR-05の折りたたみ領域へ移し、3Dの実再生と見分けられる見出しを付ける。2D模式で選択を変えても連結順と詳細タイムラインを変更しない。

`three-host.js` は現在1画面につき1ホストで、WP-04のSCR-06/12で利用する。SCR-05/13は画面遷移時に前ホストを破棄し、表示オブジェクトとmixerを自分で管理する。正規化・骨階層・テクスチャはWP-04の読み込み結果を利用し、ボーン生成、スキニング、ウェイト変更を伴う処理は入れない。

## 6. 実装単位と受け入れ試験

1. **カタログと単体再生**：82件の値が旧表と一致。登録可否の判定で欠けたFBXは再生不可。実FBXのボーンがシーク前後で動き、停止で基準姿勢に戻る。GLB内クリップはSCR-12で選択できる。
2. **コンビネーション**：3ステップを追加・並べ替え・削除して連結再生。実FBXで境界、ループ、スクラブを確認し、位置が重複加算されない。保存→再読込、Undo/Redo、旧画面との読み取り一致。未登録・曖昧なステップを追加せず、100件上限では複数ステップの一部だけを追加しない。
3. **詳細タイムライン**：連結順からの取り込みで90Fずつのコピーができ、元連結順は不変。既存詳細クリップの置換をキャンセルすると不変。開始・長さ・速度・ブレンドの保存→再読込が一致し、実3D結果と空白区間が一致する。
4. **競合と失敗**：新UI 2画面または新UIとrevision付き標準MCPの同時編集で後着が409となり、サーバーの先着データを保つ。ネット切断・ディスク書込失敗・壊れたJSONでは成功表示を出さず、元ファイルと未保存の画面編集を保つ。旧画面・旧WebMCPのヘッダーなし書き込みは従来どおり動き、**その経路との同時編集は保護できない**ため、同時に開いて編集しない旨を画面と日本語文書に示す。
5. **PMX＋VMD・レビュー**：最小PMX/VMDのボーンとモーフ、登録済み実データで再生を比較。QA・ボーンマップ・補正レイヤー・足接地の既存API応答を新UIで表示。GPU・実PMX/VMDを実行できなければ各項目を未検証とする。
6. **操作経路**：新UI手動操作と標準MCPの同じ編集をAPI readbackで比較。旧WebMCPの編集も旧画面で回帰確認するが、新UIのWebMCPはR10どおり未接続と表示する。旧画面と新画面を同時に開き、`target:'studio'` の再生は新画面だけで起き、targetなしは旧画面だけで起きる。画面を閉じた後にRAF・WebGL context・購読が残らない。1280px/狭幅・キーボード・スクロールをブラウザで確認する。

各コードコミットでP2台帳に変更ID、コミット、実行した試験、未実測の媒体・環境を記録する。`node tools/gen_screen_matrix.mjs` と実装状態の正直さのテストを実行し、実機3Dで見ていない項目を「動作確認済み」と書かない。

## 8. 設計の照合と残るゲート

- `index.html` の連結順と `timeline_editor.json` は実際に別保存である。自動統合すると片方の編集を失うため、明示コピーと別々の保存状態にした。
- `updatedAt` のGET後にPOSTする方式には競合の窓がある。DATA-001/002・DATA-011の非破壊を守るため、§0 R1の「既存APIをそのまま呼ぶ」に対する**最小の例外案**として、既存ファイル形式を維持したIf-Match追加を提案した。旧クライアントのヘッダーなし書き込みとの競合は残るので、同時編集しない案内と診断を必須にする。
- 初案は旧 `index.html` と旧 `webmcp.js` を修正しようとしていたが、§0 R5（旧画面の変更制限）とR10（新UI WebMCPの延期）に反するため取り下げた。再生コマンドはサーバー側の別キューへ振り分け、旧画面ファイルに触れない。
- フォーク元の `norm()` は異なるファイル名を同じキーに畳む可能性がある。自動一致が複数ならエラーとし、既存対応表による明示選択を必要とする。
- P2-WP-04bの移植結果を本ブランチはまだ含まない。コード着手前に④bの公開APIとSCR-13の既存タブを再照合し、同じ機能を重ねて実装しない。
- §3に指定された高性能モデルによる独立批評1回は、この文書の自己照合とは別の**未完了ゲート**。批評でR1例外や画面配置に問題が見つかれば、実装前に本書を修正する。Owner側の動作確認は求めず、GPU・実PMX/FBX/VMDの検証は実装時の台帳に残す。
