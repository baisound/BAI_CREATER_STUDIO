# mainへのPRマージ後、手元の画面を更新する手順

対象: このリポジトリのPRをGitHubの`main`へマージした直後。Issue [#33](https://github.com/baisound/BAI_CREATER_STUDIO/issues/33) に基づく運用。`recovery`など他のブランチへのマージだけなら、この手順で手元の`main`を変更しない。

## 利用者に見える結果

手元のメイン作業フォルダー`D:\BAI\BAI_CREATER_STUDIO\BAI_Creator_Studio`の`main`がGitHubの`main`と同じコミットになり、`http://127.0.0.1:8765/`がその作業フォルダーの最新版を返す。更新できない場合は古い画面を最新版と呼ばず、理由と現在のコミットを伝える。

## 安全な更新

1. マージ済みPRの番号、`main`のマージコミット、現在の`origin/main`を確認する。PRが未マージなら更新しない。
2. メイン作業フォルダーで`git status --short --branch`、`git log -1 --oneline`、`python tools/work_state.py show`を読む。利用者の変更、追跡外ファイル、進行中の別作業を把握する。追跡外の`logs/`、素材、バックアップを削除・上書きしない。
3. `git fetch origin main`後、`main`への切替が安全か確認する。追跡中のローカル変更が衝突する場合は停止し、変更を保全して理由を報告する。追跡外ファイルが新しい追跡ファイルと衝突する場合は、内容とハッシュを記録して安全な退避先へ移し、更新後に所在を伝える。無条件の`reset --hard`、`clean`、上書きは使わない。
4. メイン作業フォルダーの`main`を`git pull --ff-only origin main`で進める。fast-forwardできない場合は停止して履歴差を調べる。手元のブランチを勝手にrebase/mergeしない。
5. `git rev-parse HEAD`と`git rev-parse origin/main`が一致し、`git status --short --branch`に予期しない追跡変更がないことを確認する。追跡外の利用者データが残っていてもそれ自体は問題にしない。

## 8765番サーバーの確認

1. ポート8765の待受プロセスを調べ、そのコマンドと作業フォルダーがメイン作業フォルダーか確認する。別の人・別フォルダーのプロセスを止めない。
2. 既存サーバーが新しいファイルを返すなら継続する。プロセスの再起動が必要な場合だけ、所有者を確認した自分のサーバーを止め、メイン作業フォルダーから非表示で起動する。起動コマンドはリポジトリの現行手順に従う。
3. `http://127.0.0.1:8765/`と、変更に関係する画面やAPIへHTTPリクエストを行い、成功応答と更新後の内容を確認する。200応答だけで更新済みと判定しない。必要ならブラウザで画面を再読込し、新しい表示を確認する。実ブラウザ未確認ならその範囲を明記する。
4. ポート競合やHTTP失敗時は、PID、起動元、応答、ログを調べる。利用者の`npm run dev`を無断で停止しない。別ポートの成功を8765番の成功として報告しない。

## 記録と報告

PRとIssueに、ローカル`main`のコミット、同期結果、8765番の応答、変更画面の確認結果、未確認事項を日本語で残す。利用者には更新後の画面リンクを渡す。マージ後の同期は次の開発を始める前に終える。
