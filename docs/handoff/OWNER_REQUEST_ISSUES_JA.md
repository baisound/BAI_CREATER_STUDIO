# バイサンドの開発依頼をGitHub Issueで管理する手順

この文書は、バイサンドからこのリポジトリに関する修正・不具合調査・機能変更・UI変更などを依頼されたときに読む。一般的な相談やリポジトリと無関係な作業には適用しない。

## 依頼を受けたとき

1. リポジトリのIssueを日本語の語句でも検索し、同じ依頼を扱うIssueがあれば再利用する。なければ着手時に作成する。会話中に追加された関連条件は、同じIssueに追記する。別の問題ならIssueを分ける。
2. タイトルと本文は日本語にする。冒頭に「何に困っているか」「どうなればよいか」を、初めて読む人が画面や操作を思い浮かべられる言葉で書く。開発用の識別子や専門用語は必要に応じて後半の「技術的な補足」に置く。専門用語を使う場合も、その意味と利用者への影響を短く説明する。
3. 確認方法と、現時点で分かっていること・未確認のことを分けて書く。推測を確定した原因として書かない。権限やデータ保護など、依頼の重要な条件も記録する。
4. 依頼に画像があるとき、または診断・結果を説明するために画像を作ったときは、その画像をIssue本文かコメントへ**画像そのものとして投稿**し、表示を確認する。ローカルパスだけの記載は添付と扱わない。複数枚ある場合は、何を示す画像か説明を付ける。確認用のローカル原本は、AGENTS.md指定のオーナー確認画像フォルダにも保持する。
5. 公開リポジトリへ投稿する前に、画像と本文に秘密情報・個人情報・公開できない素材が写っていないか確認する。公開できない場合は勝手に投稿せず、公開可能な範囲の画像を用意するか、必要な判断をオーナーに求める。画像がまだ取得できないときはIssueにその状況を書き、取得後に追加する。

## 書き方の目安

```markdown
## 困っていること
（画面・操作・起きることを普通の言葉で）

## 期待する結果
（利用者が何をできるようになるか）

## 確認方法
（再現操作、または完成時に確かめる操作）

## 画像
（画像を直接添付し、各画像の説明を書く。画像がない場合は「なし」）

## 技術的な補足
（必要な場合のみ。原因候補、関連ファイル、要件IDなど）
```

## 作業中と完了時

- 作業内容や判明した原因が変わったらIssueを更新する。Issueに記した依頼とPR・コミット・検証結果を相互に結ぶ。
- 完了報告には、利用者に見える変化、確認したこと、残る未確認事項を日本語で書く。受け入れ条件が満たされたと確認してからIssueを閉じる。
- 複数の依頼を一つの作業で修正する場合も、各Issueから該当PRと結果へ辿れるようにする。未完了の依頼は、関連PRがマージされても閉じない。

この手順はIssueを作るための運用ルールであり、承認済みロードマップの優先順位やオーナーのボーンまでの担当分担を変更しない。
